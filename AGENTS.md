# Asterweave — Agent Instructions

Asterweave is an independent, open-source interactive fiction development environment created by JA Sanborn, licensed under MPL 2.0. Read the [project README](README.md) and [documentation index](docs/README.md).

## Mandatory reading and authority

Before work, inspect the current branch, relevant GitHub issue, dependencies, acceptance criteria and affected files. Read [architecture](docs/ARCHITECTURE.md), [coding standards](docs/CODE_STYLE.md), [testing strategy](tests/README.md), [contributing](CONTRIBUTING.md), relevant [contracts](docs/engine/contracts/README.md) and [ADRs](docs/decisions/README.md). Follow [security policy](SECURITY.md).

Accepted ADRs govern decisions; current normative contracts govern behavior; coding standards govern source; tests and actual results provide implementation evidence. GitHub Issues govern actionable scope and [roadmap](docs/ROADMAP.md) priorities. Future considerations are nonbinding. Use active ADRs for current decisions; the archive is historical only and outside mandatory reading; surface conflicts between docs, issues and code before proceeding. Do not silently change accepted contracts.

## Architecture and coding

- Use standard ECMAScript, ES modules and zero third-party runtime/development npm dependencies under current Foundation decisions. Node.js is permitted for development and compatible hosts.
- Keep gameplay engine and first-party gameplay modules independent of DOM, storage, networking, filesystem, graphics and Node-specific APIs. Presentation environments integrate platforms; Creator is optional authoring; Tools own compilation and distribution; interaction modules sit above the engine. Engine and Tools are independently usable; Creator uses both. Exclude Creator, development tools and unused executable modules from distributions. Tools own selective standalone bundling and game packaging outside gameplay execution; compiled game content packages are always encrypted by build Tools, with no unencrypted package variant or toggle. Direct unencrypted canonical JSON remains independently supported. Runtime loaders perform authenticated decryption and unpacking outside gameplay Engine, followed by independent canonical validation; any build-tool dependency exception requires explicit approval. Creator framework dependencies are separate and require design review.
- Follow ADRs 0051 and 0052: target source boundaries are engine, modules, interaction, creator and tools, with corresponding test and documentation responsibilities. Mandatory engine has no dependency on optional modules or higher layers; compose first-party capabilities before gameplay using explicit acyclic dependencies, not dynamic plugins. Maintain all five agreed component directories under source, tests and documentation, and the guides directory, with meaningful README files even before implementation. Introduce further subdirectories only when justified; verify actual paths and do not create speculative executable placeholders.
- Follow ADR 0054: canonical modular JSON is the approved native representation; current supported format is 4.0.0; modular loading remains planned. Direct JSON, future declarative language and Creator are independent workflows targeting common contracts; Tools own translation, assembly and coordinated validation. Creator owns visual editing, workspace management, authoring UX, playtesting orchestration and export UX; it must not duplicate validation rules or simulate gameplay independently. No executable authored scripts in the initial release.
- Follow ADR 0064: cohesive domain modules, one principal type per file, native encapsulation, composition, narrow explicit dependencies, no circular imports or global mutable state. Use independently testable domain logic and separate orchestration.
- Follow [public API](docs/engine/contracts/PUBLIC_API.md): one primary facade, engine-controlled construction, intentional documented public interfaces, compatibility review and independent version authorities. Superseded pre-release functionality, compatibility aliases and migration mechanisms need not be retained; remove obsolete code and redundant tests while preserving current contracts and meaningful distinct coverage. No public gameplay-module APIs or speculative module discovery; consumers use supported interfaces.
- Use descriptive English identifiers, required license headers and JSDoc for public and private members, and EditorConfig formatting. Avoid speculative frameworks and premature optimization.
- Commands and choices share explicit actor-identified actions and one dispatcher; neither owns world logic. Return semantic results, not rendered interfaces. Design for multiple actors and implement the single-player headless engine first; interaction and presentation remain optional.
- Keep generic world operations and reusable standard handlers separate from game policies and specialized mechanics. No public executable extension framework is planned; do not expose private registry or state internals. Date Time is a first-party gameplay module; Text Parser and Visual Novel are interaction modules above the engine. Zork is a compatibility reference, not an engine specification.

## Security, errors and state

- Follow [security model](docs/engine/contracts/SECURITY_MODEL.md) and [error handling](docs/engine/contracts/ERROR_HANDLING.md): validate external data, authorization, references and invariants; use safe algorithms and explicit resource ownership. Only trusted first-party engine code supplies executable gameplay in the initial release; authored JSON is untrusted declarative data. JavaScript encapsulation is not sandboxing.
- Preserve operation-specific diagnostics/results, domain-owned codes, deterministic aggregation, exception cause when wrapping, atomic failure and fail-closed integrity. No core operational logger; hosts own reporting and platform security.
- Use immutable isolated definitions, normalized overrides, supported engine-controlled qualified domain properties, operation-only mutation grants, six gameplay scopes and one authoritative World containment hierarchy. Derive actor location, inventory and loads; enforce lifecycle, association and capacity invariants without duplicating placement.
- No persistent instance ID, human knowledge tracking or gameplay undo. Keep detached recursively read-only snapshots and engine-owned transactions. Storage adapters remain outside core; platform-independent capture and atomic restoration are planned Foundation work. See [properties](docs/engine/contracts/PROPERTIES.md), [runtime state](docs/engine/contracts/RUNTIME_STATE.md) and [save data](docs/engine/contracts/SAVE_DATA.md).

## Testing and completion

Follow the [testing strategy](tests/README.md) and definition of done. Test relevant domain, contract, integration, security, negative, boundary, determinism, isolation and architecture behavior; test hosts separately. Use native tooling and meaningful behavioral coverage. Report actual checks/results and limitations. Do not claim planned capabilities are implemented or tested. Distribution Tools must verify applicable source validation, integrity, dependencies, capabilities, public interfaces, source-to-bundle and direct JSON versus decrypted package equivalence, offline execution, exclusion of unnecessary modules/tools and licensing compliance. Required check failures prevent successful builds; never weaken encryption for byte-identical artifacts.

When a supported local test environment is unavailable, use the existing GitHub Actions CI on an authorized feature, fix, refactor or docs branch. Commit a focused increment together with its applicable tests, then verify the CI run for that exact commit SHA, including the test job conclusion and relevant logs. Until successful verification, treat the increment as unverified; correct failures before advancing to another implementation increment. Missing, queued, cancelled or inaccessible results are not passing tests. Remote verification does not authorize a pull request, merge or issue closure.

## Issue-driven workflow and authorization

- GitHub Issues are the authoritative backlog. Search existing issues before creating new ones; use templates and testable acceptance criteria. Track defects as bugs.
- Brainstorming or review does not authorize issue creation, repository changes or implementation. Respect explicit scope and approval; documentation approval does not authorize code. Discuss significant architecture, dependencies and breaking changes first.
- Use focused feature, fix, refactor or docs branches. Open PRs targeting main when authorized; do not create a PR when the user requests branch-only work. Reference issues; use closing keywords only when criteria are fully met.
- Never bypass branch protection, commit directly to main without explicit authorization, merge without authorization or close issues without authorization and evidence of completion.
- Update affected tests, docs, indexes and ADRs as appropriate. Preserve historical decisions and record accepted changes. Verify commits and report progress accurately.

## Licensing and safety

Preserve LICENSE, NOTICE and AUTHORS.md. Include MPL Exhibit A notices and SPDX-License-Identifier: MPL-2.0 in covered source files and preserve required distribution notices. Never commit credentials, unpublished private stories, local saves or generated builds. Report vulnerabilities privately under SECURITY.md. Prioritize small, working, tested increments over feature breadth.

Active ADRs in `docs/decisions/` begin at 0051; archived identifiers are never reused. Reconcile outdated technical contracts and source deliberately; accepted architectural direction is not evidence of implementation.
