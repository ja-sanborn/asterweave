# Runtime state

Status: Accepted contract. See [properties](PROPERTIES.md), [save data](SAVE_DATA.md), ADRs [0013](../decisions/0013-namespaced-properties-and-runtime-state.md), [0014](../decisions/0014-player-identity-and-state-scopes.md) and [0015](../decisions/0015-state-isolation-and-persistence.md).

## Authority and scopes

Each runtime has one authoritative current state: immutable, isolated authored baseline plus current normalized overrides and supported dynamic data. Independent runtimes share no mutable state. No persistent game-instance identifier. Game ID/content version identify the baseline; world participant IDs follow the [containment contract](WORLD_CONTAINMENT.md). Save IDs, session IDs, authentication, connection state and presentation preferences belong to hosts/storage, never core gameplay state.

| Scope identifier | Subject |
| --- | --- |
| world | implicit singleton, no id |
| location | authored location id |
| entity | authored entity id |
| actor | authored actor id |
| player | runtime player id |
| relationship | ordered pair of typed endpoints |

Override records are closed objects with scope and scope-specific identity (id for location/entity/actor, from/to for relationship, none for world), optional values map and optional removed array; at least one must be nonempty. For Foundation, player records store complete current properties separately, not player override records, because they have no authored baseline. Relationship endpoints are closed {scope,id} references for location/entity/actor/player, or {scope:"world"} for World. Authored initial relationships cannot reference players because they are runtime-created. References must exist and have correct scope; inactive/destroyed world identities can retain nonphysical relationship state. Direction matters; reverse is independent. Self relationships are allowed as nonphysical data. One record per ordered pair; namespaced keys distinguish multiple kinds of relationship. Empty relationship state has no independent identity. Containment is not a relationship-scope record.

```json
{"scope":"relationship","from":{"scope":"actor","id":"guide"},"to":{"scope":"actor","id":"adventurer"},"values":{"stateFoundation.trust":3}}
```

## Initial candidate state

Under [ADR 0016](../decisions/0016-modular-architecture-and-design-patterns.md), initialization maps structurally validated canonical data into an isolated normalized candidate through GameDefinitionMapper, resolving documented baseline defaults. Validate effective-record structural prerequisites, shared domain invariants, initialization-specific viability and applicable initialization configuration before finalizing the immutable baseline and publishing an independent game. Candidate data is not committed state; discard invalid candidates. Standalone definition validation uses the same applicable mapping and invariant checks without constructing a public game. Domain validators depend on effective values, not canonical JSON paths or override/save storage. Runtime transactions and future restoration must reuse these invariants with their own candidate representations and operation-specific translation. The requirement for an active location and active actor is initialization viability, not an ongoing invariant. Preserve existing initialization diagnostics and ordering. Apply forward-transition rules separately during gameplay; reset and future restore validate replacement state, not forward transitions from the previous running state (restore must still respect baseline restrictions under the save contract). Do not introduce duplicate authoritative state or duplicate domain rules.

## Players and actors

Players do not exist in physical World. Foundation permits zero (headless testing) or one player; future hosts may support more. Player IDs follow world ID grammar but use a separate scope; they are not accounts. Runtime initialization explicitly supplies optional player configuration, including id, controlled actor IDs and optional selected actor; no implicit player from an actor name. Retain a detached initialization configuration for reset. Initial player state is runtime-created and stored fully, not duplicated in override records. Player properties include required asterweave.controlledActors (distinct actor IDs, ordered array) and optional asterweave.selectedActor (actor ID in the controlled list); omission means no selected actor, including when no actors are controlled. Other game/extension properties follow common rules.

The optional second argument to initializeGame is a closed options object. Omission means no explicit player; its only supported key is player. If supplied, player is a closed object with required id and controlledActors (ordered distinct active actor IDs), optional selectedActor and optional initialProperties. Omit selectedActor to leave selection absent even for a single controlled actor. An empty controlledActors array is allowed. Reject unknown fields, non-data input, invalid references or values; do not coerce or infer defaults beyond documented omissions. initialProperties is a qualified game-owned property map (omission means empty); reject reserved asterweave keys and unavailable extension namespaces. The engine derives controlledActors and selectedActor properties from their dedicated fields, not from initialProperties. Preserve a detached immutable copy of original configuration for reset; store complete player state separately from authored overrides. No credentials, host settings or human knowledge tracking.

Only active actors can be controlled; an actor has at most one controlling player. Control changes and lifecycle changes must resolve selection/control atomically. Game logic may direct non-player actors; trusted gameplay logic is distinct from player-authorized requests. Actions retain explicit actorId; the host/public entry point must validate player control when operating on behalf of a player, never infer authorization from actorId alone. The accepted trusted internal headless submission path may operate without a player through an explicitly authorized internal path; absence of a player does not itself grant authority. No accounts, authentication, networking or multiplayer implementation in Foundation. Actor-to-player lookup is derived.

Initialization configuration diagnostics use source options and JSON Pointer paths relative to the options argument, for example /player/controlledActors/0. Definition findings use source definition; both belong to one ordered collection, with definition findings first. Independent safe configuration checks may proceed despite invalid definition data, but checks requiring invalid prerequisites must be suppressed. See [error handling](ERROR_HANDLING.md).

## Transactions and snapshots

Follow the [error-handling contract](ERROR_HANDLING.md) for atomic failure, exception translation and fail-closed integrity. A failed operation may leave a usable runtime when committed integrity is assured; otherwise prohibit further gameplay mutations. Recovery and public read restrictions follow the administrative reset and integrity contract below.

All gameplay mutations are staged within an authorized action transaction. Validate property ownership and component restrictions, effective core invariants (including world hierarchy, lifecycle, associations and capacities), actor control and turn costs before committing. Rejected/error results discard all staged changes, turns and gameplay outputs. Completed failure may commit intentional valid consequences under ADR 0006. No direct public writable state reference/setter. Reset and future restore are separate atomic administrative operations; they do not consume gameplay turns. Reset clears overrides and dynamic data, restores authored defaults and original initialization configuration, and does not affect external saves.

Snapshots are detached, recursively read-only effective values, including unchanged authored values and current overrides; later gameplay cannot alter earlier snapshots. Copy arrays/objects before freezing; never freeze caller input or expose live state. Snapshot/derived query order is deterministic; use stable case-sensitive code-unit ordering for identifiers/keys, preserve semantic array order. Cache only if observable behavior is identical. No duplicate authoritative inventories, locations, loads or actor-to-player mappings. Trusted snapshots are not automatically safe for player exposure; future hosts enforce authorization and scoped outputs.

World asterweave.turn starts at 0, is a nonnegative safe integer and advances exclusively through dispatcher-selected completed outcome costs. Reject overflow atomically. Zero-turn completed actions may change state; real-world elapsed time does not advance gameplay. Restore/reset may replace the counter administratively. All actors share it. Future events, RNG and calendar state preserve deterministic continuation when implemented.

### Staging, validation and authority

RuntimeState owns committed state and composes an encapsulated Map-based override store. Share the immutable baseline with a single isolated candidate of mutable overrides and complete player records; derive effective state on demand. Internal indexes are independent of serialized records. Use structured scope and ID addresses and typed relationship endpoints, with shared property resolution and domain-owned mutation authority. Use one effective-value resolution mechanism for world/domain reads, snapshot construction, handler reads and candidate validation, preserving isolated committed and candidate views. Player records remain separately owned. Do not maintain a second authoritative effective-state representation or introduce speculative caches.

Only one action transaction may be active per runtime. Guard dispatch and reset before inspecting external input; nested/reentrant operations reject without affecting the outer operation. Candidate reads observe staged writes, public reads observe committed state only. Revoke handler capabilities at exit, including exceptional exit. No writable references escape. Stage outputs and prepare the result before the final atomic commitment; discard candidate and outputs on rejection or error. Do not retain transaction history. The accepted internal transaction lifecycle, state-reader ownership and publication mechanism are described in the [runtime implementation design](../RUNTIME_IMPLEMENTATION.md#candidate-lifecycle-and-publication).

Validate ownership, JSON structure, identity and local preconditions at mutation time. Before commitment validate the complete candidate and transition from committed state: protected properties, lifecycle, containment, associations, capacity, control, selection and checked turn progression. Establish required effective-record shapes, supported identifiers and values, types and ownership prerequisites before invoking invariant checks. Reuse shared pure constraints and domain rules with initialization, preserve diagnostic cascade suppression and independent valid-branch findings; do not reconstruct authored data to validate runtime state. Destroyed participants remain terminal in forward transitions. Intermediate candidate states may temporarily violate cross-domain invariants while coordinated changes are staged. Expected domain rejection leaves the attempted change unstaged; programming or integrity failures invalidate the transaction even if caught by handler code.

Control assignments are ordered, distinct active actor IDs; selection is optional and must refer to a controlled actor. Revocation removes control and clears affected selection atomically. Planned Foundation lifecycle operations that deactivate or destroy an actor must do the same, together with required descendant, containment and physical-association cleanup. Runtime validation must enforce these invariants now; general activation, deactivation and destruction of existing participants are planned Foundation operations; dynamic creation remains deferred. Dedicated control and selection operations are included; generic game-property mutations cannot alter lifecycle or control. Trusted internal tests may construct candidate transitions without adding a public testing backdoor or production lifecycle handler. Do not infer a replacement selection or restore control on reactivation. Granting already established control, revoking a known uncontrolled actor and clearing absent selection are valid no-ops. Granting or selecting requires an active known actor, and selecting requires existing control. Unknown actor references are invalid. Reverse lookup is derived. Ordinary player-property reset uses the original initialization value or absence; control and selection remain subject to dedicated operations and current actor invariants.

### Administrative reset and integrity

The synchronous public reset operation rebuilds and validates original initialized effective state before atomically replacing committed state. Clear overrides, removals and dynamic properties/relationships; restore initial turn and detached original player configuration. Retain immutable baseline, facade and finalized registry. Earlier detached snapshots and results are unchanged; external saves are unaffected. Reentrant reset rejects. ResetResult follows [error handling](ERROR_HANDLING.md#reset-result).

An isolated candidate failure does not compromise verified committed state. If committed integrity cannot be established, block gameplay and unverified state reads. Dispatch returns EXECUTION_FAILED; turn and getStateSnapshot() throw a safe native Error. Verified immutable game metadata remains readable. Reset may recover only after checking the reconstructed state and trustworthy retained dependencies: immutable baseline structural/domain invariants, original initialization configuration, world identity consistency, original turn, empty overrides, player records, and action registry ownership, finalization and structural contracts. Verification is bounded to engine-controlled state and contracts; it cannot establish correct executable behavior or repair an untrustworthy JavaScript environment or external effects. Failed recovery leaves an already compromised runtime blocked and publishes no candidate; ordinary reset failure preserves verified committed state. If recovery cannot establish integrity, establish a trustworthy environment before initializing a new runtime. No public health status, selective reset, gameplay undo or recovery history. See [ADR 0025](../decisions/0025-runtime-reset-and-integrity-recovery.md).

## Effective state snapshot

The public getStateSnapshot() method provides effective state inspection. Use the same interface for committed gameplay state; do not introduce a temporary or incompatible snapshot schema. Construct snapshots on demand as detached, recursively read-only, ordinary JSON-compatible data. A snapshot is neither a canonical definition nor a save file.

The root has the following required fields:

| Field | Shape |
| --- | --- |
| game | Record containing id, title, namespace, version (content version), formatVersion (definition format version) |
| world | Record containing properties |
| locations | Array of records containing id, properties, exits |
| actors | Array of records containing id, properties |
| entities | Array of records containing id, properties |
| players | Array of records containing id, properties |
| relationships | Array of records containing from, to, properties |

All fields are required; empty collections are empty arrays. Properties are maps of all applicable effective qualified values, including resolved engine defaults, unchanged baseline values and current overrides. Missing or removed values are omitted; explicit null, false and zero are preserved. Do not include override records or removal markers. The structural id identifies the record; where the property contract defines asterweave.id, its effective value agrees with that identity. Location exits are detached immutable Foundation definition data, preserving authored array order. Include inactive and destroyed participant identities. Directed relationships use the typed endpoints defined above; omit records with no effective relationship properties.

Sort each participant and player collection by ascending case-sensitive ECMAScript code-unit ID order. Sort relationships by source scope, source ID (absent for World), destination scope, then destination ID, using the same ordering. Construct property maps in code-unit key order; preserve semantic array order, including controlled actors, exits and arrays within property values. JSON object member order is not semantic. Containment is represented by the effective qualified property, not an additional placement field. Do not include derived inventories, effective actor location, recursive contents, physical loads or reverse actor-to-player lookup as independent snapshot fields.

Snapshots support native JSON serialization, contain no live engine objects, credentials or host session data, and have no independently versioned format. Compatibility follows engine API SemVer. Full snapshots are trusted inspection data, not authorized player-visible descriptions; hosts must enforce audience boundaries. Future derived queries and player perception interfaces are separate contracts.

The independent action registry is privately owned by the facade, not RuntimeState. Its definitions, handler associations and authority capabilities are excluded from effective-state snapshots and saved gameplay data. Administrative reset retains the finalized registry. See [action definitions](ACTION_DEFINITIONS.md).

## Knowledge and future capabilities

No core knowledge/discovery subsystem, human player knowledge tracking or gameplay undo/back navigation. Player-controlled actors do not track knowledge by default. NPC or fictional character knowledge is optional game/extension state; actual world changes persist. Visibility/accessibility are evaluated by gameplay rules. Interaction/narrative context is persisted only where a future gameplay contract requires it; host state remains outside. Transaction rollback is not gameplay undo. Restore earlier independent saves to return to earlier state. Visual novel backward navigation is out of scope.

Randomness, pending events and supported extension state require explicit Foundation state contracts; dynamic world participants and reserved IDs/allocation remain future work; preserve complete necessary dynamic data and deterministic continuation without unused placeholders. Current infrastructure provides property/control/state operations; lifecycle gameplay operations and shared perception/access are planned Foundation work. Dynamic creation and parser implementation remain outside Foundation. See [fixture](../../tests/fixtures/games/state-foundation.json).
