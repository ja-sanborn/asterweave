# Runtime implementation design

Status: Accepted detailed design; implementation and verification of the execution and reset capabilities remain pending. This document describes internal collaboration, not a supported public interface or an implementation progress record. [Architecture](ARCHITECTURE.md), [runtime state](contracts/RUNTIME_STATE.md), [properties](contracts/PROPERTIES.md), [action definitions](contracts/ACTION_DEFINITIONS.md), [action and result contracts](contracts/ACTIONS_AND_RESULTS.md), [error handling](contracts/ERROR_HANDLING.md) and [public API](contracts/PUBLIC_API.md) govern behavior. See [ADR 0024](decisions/0024-runtime-transactions-and-action-execution.md) and [ADR 0025](decisions/0025-runtime-reset-and-integrity-recovery.md).

Internal names and signatures below describe accepted design intent; reconcile them with existing source and reuse equivalent helpers before implementation. Material changes to responsibilities, authority or contracts require review. Preserve current domain dependency direction, one principal class per file, native encapsulation and composition. Stateless calculations and validators remain pure functions. No additional dependencies, format versions or public extension interfaces.

## Module ownership

| Principal class | Domain | Responsibility |
| --- | --- | --- |
| PropertyOverrideStore | state | Private normalized differences and candidate cloning |
| EffectiveStateReader | state | On-demand effective property and relationship resolution |
| StateTransaction | state | Candidate ownership, staging and lifecycle |
| ActionExecutionContext | state | Restricted invocation-scoped access and authority |
| ActionDispatcher | core | Synchronous action orchestration |
| RuntimeResetter | core | Administrative reconstruction and recovery orchestration |
| ActionResult | results | Immutable gameplay result |
| ResetResult | results | Immutable administrative result |

Extend RuntimeState, Player, ActionRegistry, GameInitializer and the existing Asterweave facade; reuse GameBaseline, World, OperationResult and existing world/domain helpers. Actions must not import state or core; state must not import orchestration or public results. Registry executable associations carry data describing separately established grants, not state-domain objects or writable capabilities. Keep existing architectural checks authoritative.

## Addresses, equality and normalized storage

Use closed address records: `{scope: 'world'}`; `{scope: 'location' | 'entity' | 'actor' | 'player', id}` (one literal scope); or `{scope: 'relationship', from, to}` with closed typed endpoints of nonrelationship scope. World endpoints omit id. Keep the qualified property key separate. Resolve exact identity and category using existing physical identity and separate player mechanisms; no competing registry. Inactive/destroyed identities can resolve; eligibility and authority are separate. A valid directed pair can have no stored properties. Compare addresses by typed identity and ordered endpoints, not object identity. Proposed helpers: validatePropertyAddress, resolvePropertySubject, arePropertyAddressesEqual.

Use a shared pure iterative areJsonValuesEqual utility on already inspected JSON data; scalar value/type equality (negative zero equals zero), ordered arrays, unordered own object key sets. No serialization comparison, getters on caller data or arbitrary depth limit.

PropertyOverrideStore owns private nested Maps indexed by scope and subject, with typed nested from/to indexes for relationships, a value Map and removal Set per subject. Never expose mutable indexes or use delimiter-composed identities. Normalize baseline-equal assignments, absent removals and resets; remove empty subject/index branches. A key cannot have both a value and removal marker. Player is excluded from authored overrides. Proposed operations: getDifference(address, key), set(address, key, value, baselineEntry), remove(address, key, baselineEntry), reset(address, key), clone(), listOverrides(). Validate authority, data and eligibility before storage; deterministic detached enumeration follows the state contract, not insertion order. Clone collection structures independently; share only recursively immutable values and baseline.

## Effective reads and player operations

EffectiveStateReader composes baseline, override and player read capabilities for one state view. Proposed operations: getProperty(address, key), hasProperty(address, key), getProperties(address), getInitialProperty(address, key), listRelationships(). Property entries are closed records `{present: true, value}` or `{present: false}` (value omitted); invalid subject or scope is a separate failure, not absence. Single-property resolution is authoritative: removal, override, then baseline; complete records reuse that resolution over the union of baseline and override keys. Player reads resolve complete current player records with identical presence semantics; initial reads use original configuration. Omit empty relationships; preserve code-unit order where required and semantic array order. No duplicated effective state or speculative caches. World and WorldObject callbacks resolve the current committed reader after publication/reset, not a stale captured reader. Snapshot construction detaches effective data.

Player retains immutable identity and one complete authoritative property record. Control and selection accessors derive from it. Proposed internal operations: controlsActor, grantControl, revokeControl, selectActor, clearSelection, setProperty, removeProperty, resetProperty, clone. Grant only active known actors; append new control, repeated grant is a no-op. Revoke known uncontrolled actor is a no-op; revocation preserves remaining order and clears affected selection atomically. Select only controlled active actor; clear absent selection is a no-op. Never infer selection. Unknown actors are invalid references. Use narrow actor identity/eligibility collaborators and shared validation. Ordinary property reset uses original presence/value; protected control and selection cannot use generic mutation/reset. Clone independent candidate records, share only immutable values. No unrestricted Player exposure or general participant lifecycle operations.

## Shared validation

Separate representation-specific checks, effective structural prerequisites, shared domain invariants and operation-specific requirements. Proposed pure functions: validateEffectiveStructure(stateView), validateEffectiveState(stateView), validateStateTransition(committedView, candidateView), validateInitialViability(stateView). Reuse existing lifecycle, containment, association, capacity, property and player validators; extract initial active actor/location viability without changing existing diagnostic codes/order. Effective structural checks precede dependent traversal; preserve independent findings and suppress cascades. Local mutation checks enforce identity, shape, ownership and local prerequisites; complete candidate checks enforce cross-domain invariants and forward transitions. Reset does not compare forward transitions against prior running state. Domain findings are translated at operation boundaries. No authored JSON reconstruction, universal validation framework or duplicated rules.

## Candidate lifecycle and publication

StateTransaction owns an independently mutable candidate override store, optional cloned Player, reader and ordered outputs; share immutable baseline. The authoritative candidate turn is the protected world property, not a duplicate counter. Four internal lifecycle states: active, invalidated, committed, discarded. Active may commit or discard; invalidated may only discard; committed/discarded are terminal. Expected gameplay restrictions leave the attempted change unstaged; programming, authority, malformed mutation and integrity violations permanently invalidate even when caught. Proposed operations: isActive, isInvalidated, getProperty, hasProperty, stagePropertySet, stagePropertyRemoval, stagePropertyReset, stageOutput, advanceTurns, invalidate, discard, plus delegated player operations. No handler access to transaction lifecycle or publication.

RuntimeState owns a single shared operation guard for dispatch/reset, and a minimal prepared-state publication path. Guard before external inspection; use reliable finally cleanup. Public reads see committed values while candidate reads see staged changes. Reentrant operations reject without automatically invalidating the outer transaction. Prepare all validation, allocation, immutable results and replacement state before publication; no external callback or fallible domain operation after publication. Only validated reset recovery may clear compromised integrity. Release abandoned resources and expire capabilities; no journals, nested transactions, savepoints, history or reliance on garbage-collection timing.

## Restricted execution and dispatch

Invoke trusted handler(action, context) with detached recursively immutable validated action data and ActionExecutionContext. Proposed capabilities: getProperty, hasProperty, setProperty, removeProperty, resetProperty, grantControl(playerId, actorId), revokeControl(playerId, actorId), selectActor(playerId, actorId), clearSelection(playerId), emitOutput. Reads return immutable presence entries; mutation delegates to authoritative domain operations. Trusted engine setup separately establishes immutable property namespace and explicit domain-operation grants; default no generic or protected-domain mutation authority. Namespace grants are upper bounds, not exemptions from scope/ownership/invariants. No authority inheritance from actor control or registration ownership. Keep executable association grants independent of authored metadata; controlled setup path must not permit self-grant by a registration owner. No public permissions framework.

Expire context immediately when handler returns or throws, before outcome inspection, and release transaction reference. Expired operations throw safely without accessing state. An invocation-local violation marker remains through outcome inspection so a detected expired-context attempt during reflective inspection prevents commitment even if caught. Clear the marker association afterward; late use cannot invalidate a later transaction. Trusted JavaScript is not sandboxed.

ActionDispatcher provides internal dispatchPlayerAction(action) and dispatchTrustedAction(action, authority) over one private sequence; no caller-controlled bypass Boolean. Guard and verify integrity, safely detach envelope, resolve active actor, authorize, resolve finalized enabled registration, validate arguments, resolve declared runtime reference existence/category, construct candidate, invoke handler, expire context, inspect outcome and invocation validity, stage registered cost, validate complete candidate and outputs, prepare immutable result, publish completed candidate, and release resources/guard. Reject/error discards candidate. Preserve earliest failure and safe echo under action/result contract.

Reuse existing safe data inspection, identifiers and argument validators; proposed validateActionEnvelope and resolveActionReferences functions belong in actions and state respectively. An internal already-inspected argument path may avoid redundant copies only if it preserves the untrusted standalone validation boundary. Reference validation retains identifier strings and never exposes live domain objects. Specialized validators remain pure and synchronous. Share native Promise rejection observation where safe, never await or assimilate arbitrary thenables, retain separate return-shape checks.

Handlers return closed records `{status: 'completed', outcome: 'success' | 'failure'}` (one literal outcome) or `{status: 'rejected', error: {code: ...}}` with only applicable safe rejection details allowed by the action error contract. Dispatcher validates and translates rejection; handler cannot declare execution error or return turns, outputs, correlation fields or transaction references. Malformed outcomes and unexpected exceptions are execution errors. No gameplay-specific branching.

## Turns, outputs and results

Dispatcher selects the registered success/failure cost; StateTransaction advances asterweave.turn using shared checked nonnegative safe integer arithmetic. No separate clock or per-turn iteration until scheduled events exist. Zero-turn mutations are valid. Overflow discards candidate. Stage outputs in emission order, validate closed records, JSON object payload and audience references at staging, recheck state-dependent constraints before commitment; do not sort/deduplicate or deliver callbacks. Outputs are included only for completed outcomes. Hosts own rendering, filtering and delivery. No output history or scheduler.

ActionResult and ResetResult extend OperationResult without overriding its five predicates. Engine-controlled internal factories: ActionResult.completed({actorId, requestId, outcome, turnsAdvanced, outputs}), ActionResult.rejected({actorId, requestId, error}), ActionResult.error({actorId, requestId, error}); ResetResult.completed(), ResetResult.rejected(error), ResetResult.error(error). Follow existing controlled-construction conventions. Reject contradictory fields; rejected/error actions have zero turns and empty outputs. Action error requires code and permits safe JSON-compatible details under its existing contract; reset error contains only code. Do not invent message requirements. toJSON returns detached operation-specific envelopes, omits absent fields and predicates; no runtime references or exception internals. Prepare before publication.

## Reset, integrity and facade

RuntimeResetter acquires the same guard, verifies retained baseline/configuration/identity indexes and registry ownership/finalization/structure, reconstructs fresh empty overrides and original player state/turn from immutable sources, validates initial effective state, prepares ResetResult, and atomically publishes through RuntimeState. Reuse initial construction and domain validation without invoking the public initialization pipeline or replacing facade/registry. No unverified committed state as reconstruction source.

RuntimeState keeps private operational/compromised integrity status separate from guard and transaction lifecycle. Isolated failure preserves verified state; uncertainty blocks gameplay and unverified reads. Only successful validated reset restores operational integrity after compromise; failed recovery remains blocked. Recovery cannot prove executable behavior or repair an untrustworthy environment. Follow public API for fixed safe read errors and verified metadata access.

GameInitializer validates, constructs immutable baseline and RuntimeState, creates/finalizes independent registry, constructs dispatcher/resetter bound to stable runtime and registry, constructs frozen facade and prepares InitializationResult before publication. Facade privately retains stable collaborators, delegates dispatchAction to player submission and reset to resetter; no preinspection outside guard, public trusted submission, registration or test backdoor. Existing metadata, snapshots, initialization and result interfaces remain intact. Production registry remains empty until real handlers exist.

## Verification

Follow [testing strategy](../tests/README.md): native component, integration, public API, security, architecture and regression tests. Test complete before/after snapshots on rejected/error paths, both completed outcomes, caught violations, reflective reentrancy, expired context during inspection and later execution, safe arithmetic, output order and recovery. Use trusted test-only handlers through controlled internal construction, never production placeholders. Implement cohesive dependency-ordered increments with accompanying tests and exact-commit CI before advancement; actionable sequencing and evidence belong in the backlog, not this design. Review OOP, SOLID, DRY, KISS, YAGNI, security, ownership, licensing and future Zork-style requirements before completion. Design-level compatibility does not establish playable Zork support. Containment transfers, production movement, general lifecycle operations, parser, choice/narrative, events, persistence, hosts and multiplayer remain deferred.
